## Important limitations in the current implementation

The protocol is a better correctness foundation than last-write-wins, but there are several gaps I would address before calling it
complete:

- Conflict resolution is not implemented. A 409 currently becomes a sync error in ios/bochi/Sync/SyncManager.swift:302, while the
  local row stays dirty. Retrying unchanged will conflict again. The app needs an “accept remote / keep mine / merge” resolution
  path.

- Operation IDs can collide across devices or reinstalls. They are derived from entity ID plus a device-local generation, but
  contain no installation namespace. Two fresh devices making their first edit to the same record can generate the same operation
  ID. Persisting a random UUID with each dirty mutation would be safer.

- Simultaneous duplicate requests have a server race. Processed-operation lookup happens before the per-user revision lock at
  backend/src/api/sync.rs:2437. Sequential retries are idempotent, but two identical requests arriving concurrently can both
  initially miss the receipt. The lookup should be repeated after acquiring the user lock.

- Lost response followed immediately by another edit to the same record is not always recoverable. The newer generation replaces
  the old operation ID locally. The server’s mixed-retry recovery works when another processed sibling operation remains in the
  request, but a single-record batch can lose that evidence and conflict.

- Theme palettes are an exception: they have idempotent operation IDs but no baseRecordRevision, so concurrent palette edits
  effectively use server arrival order.

- processed_sync_operations currently has no retention policy, so the table grows indefinitely.

  ## What generations do not solve

  Mutation generations do not solve server conflicts.

  For example:

  Device A Task A local generation = 101
  Device B Task A local generation = 101

  Those values have no relationship. They come from separate local databases.

  Server conflicts are still determined only by:

  operation.baseRecordRevision
  versus
  current row.serverRevision

  Generations also do not merge edits or order operations across devices.

  ## Current limitations

  The intended retry flow works, but the current implementation has some gaps.

  ### Cross-device operation ID collisions

  The operation ID input contains:

  entity kind + record ID + local generation

  It does not contain a device/installation identifier.

  Two devices for the same user can independently generate:

  Task A generation 1

  and therefore construct the same operation ID. Because server receipts are keyed per user, the second device’s legitimate edit
  could be mistaken for a retry from the first.

  A safer design would store a randomly generated operation UUID directly beside each dirty row:

  dirty_records:
      user
      entity kind
      record ID
      mutation generation
      operation ID

  A new local mutation would create a new UUID, while retries would reuse the persisted UUID.

  ### Lost response followed by a newer local edit

  If Operation X commits but its response is lost, then the user edits the same row again:

  generation 101 / Operation X → committed, response lost
  generation 102 / Operation Y → now stored locally

  The local dirty row no longer retains Operation X. It only reconstructs Operation Y.

  Unless another operation from the old batch supplies missed-response evidence, the server may reject Operation Y because its local
  baseRecordRevision is still stale.

  A proper durable outbox would retain acknowledged-but-unconfirmed Operation X until its result had been reconciled.

  ### Concurrent identical HTTP retries

  The server checks processed operation IDs before acquiring the per-user revision lock. Two identical requests arriving
  simultaneously can both initially observe no receipt.

  The lookup should be repeated after acquiring the per-user lock, or processing should begin by atomically claiming the operation
  IDs.

  So the concise distinction is:

  mutation_generation:
      local per-user allocator
      stored per dirty row
      distinguishes successive local versions
      protects edits made during in-flight sync

  operationId:
      per dirty row version
      stable across retries
      lets the server recognize an already-committed operation

  serverRevision:
      server-side per-user allocator
      stored per server row
      detects concurrent server changes

  Together, generations and operation IDs provide durable retry identity and safe local finalization. They are separate from the
  server-revision mechanism used for conflict detection.
